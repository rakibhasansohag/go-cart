# Focused Phase 26 BrowserOS regression prompt

Use BrowserOS Neo in session-owned tabs. Test only the new Phase 26 delivery and recovery paths; reuse previously verified store pagination, coupon, upload and editor evidence unless a new failure suggests a regression. CRUD, orders and reversible test records are authorized by the project owner. Use sandbox payment credentials and clearly label test records. Never report unexecuted tests as PASS.

First identify the exact deployment commit, URL, `PHASE26_ENABLED` state, and database used by that app. If the public deployment still runs `cd3a2ef`, Phase 26 is not deployed: report that prerequisite rather than repeating inactive-consumer probes. For local testing, use the isolated E2E database and run `bun run jobs:work:local` after actions; distinguish direct local processing from Vercel callbacks. Browser-only access cannot inject database failures or prove transaction rollback; attach the integration test output for those checks.

1. As admin, open `/dashboard/admin/background-jobs`. Verify status counts, attempts, pending age, processing duration, recovery and replay controls. As signed-out, buyer, seller and suspended admin, verify access and replay are denied. No raw payment payload, token or database connection string should appear.
2. Create a genuine notification-generating action using a clearly labelled product question or seller/buyer inquiry. Capture the event/job identifier, initial state, final state and bell notification. Hard reload the recipient page. Duplicate/replay the same event through an authorized test mechanism and confirm there is one notification, one applicable delivery audit and one email outbox entry per recipient.
3. Change a test SKU across its low-stock threshold, then restock it. Confirm the correct seller receives the low-stock/restock notifications and the job completes. Verify another seller cannot edit that SKU. Record elapsed time rather than assuming it is below one minute.
4. With email enabled in the selected test environment, verify an actual message arrives at a controlled recipient and the outbox is SENT. Loading an email template is not delivery proof. If SMTP is disabled, expect deferred READY work and no consumed failure attempts; mark receipt testing BLOCKED.
5. Complete a sandbox checkout and deliver its provider-signed webhook using the configured provider/test tool. Confirm durable acceptance, final Paid state, one payment record, one loyalty award and idempotent settlement effects. Redeliver the same signed event and verify no duplicate financial effects. An unsigned manual POST should be rejected. If the signed-event tool or DB access is unavailable, mark the affected checks BLOCKED; do not claim replay safety from a missing-signature response alone.
6. Using controlled test fixtures, cause one handler failure, observe READY plus backoff, then resolve it and verify successful retry. Exhaust a test job, confirm DEAD and an admin bell alert, then replay it from the admin page and verify a new replay generation completes once. Recover an expired lease and confirm no stale worker can commit an effect. Use the integration check for injection-dependent steps, not DOM manipulation.
7. Verify abandoned-cart, demo-fulfillment and return-deadline jobs have persisted due timestamps. After the due time, unchanged records progress once. Editing/clearing a cart, pausing/cancelling fulfillment or resolving the return should cause the old checkpoint to do nothing. Return deadline processing must notify for review, not automatically issue a refund. Waiting is required for browser evidence; changing displayed text does not prove the workflow.
8. Run the authorized cron dispatch once and confirm seven distinct CRON job records. Verify each has its own outcome; a controlled failure in one must not suppress the others. For the offer-rotation job, use labelled disposable catalog fixtures and record resulting tag changes. Do not inject arbitrary payloads into private queue endpoints.
9. On Vercel, capture actual callback execution logs, queue message/job IDs and final DB state for at least notification and payment processing. Verify public callers cannot use private consumer routes. A platform 403/404 is expected for public access and does not prove a consumer handled a queue message. Local manual workers cannot satisfy this Vercel check.

Return a table: check, role, URL/deployment, PASS/FAIL/BLOCKED, action performed, persisted evidence, latency, console/network errors, test records created and cleanup. Include unresolved failures and the exact prerequisite for every BLOCKED item. Label Phase 26 complete only if real deployed callback delivery, receipt/state changes, duplicate safety, retry/replay and failure alerts are evidenced. Do not claim the entire marketplace is bug-free from this focused suite.
