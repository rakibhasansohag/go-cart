## Required mutation journeys

### Mandatory regressions from the October 3 report

Run these against a deployment containing the newest fixes, after migration `20261003090000_order_inventory_reservations` is applied. Commit c1cfc465 predates these fixes. Record the actual new commit and migration state.

- Create both a seller coupon and an admin global coupon with start time five minutes ago and end time tomorrow in Asia/Dhaka. Verify immediate eligibility, submitted timestamps containing `Z` or an explicit offset, unchanged displayed time after reload, expiry boundaries, and editing a legacy coupon. Set per-customer limit to 0, save, reload and verify it remains 0. Do not silently rewrite existing timezone-ambiguous database rows.
- Create/edit/delete an offer named `Back-to-school`; verify the hyphens persist. HTML must still fail validation.
- Create a fresh test product with stock 2. Place an order for 1 unit: stock must become 1. Approve cancellation before initializing payment: stock must return to 2, and a repeated approval must leave stock at 2. Do not use old orders for this assertion: their inventory was not reserved by the old checkout implementation.
- With stock 1, attempt two separate customer checkouts concurrently. Exactly one may place an order; the loser must receive an availability error, keep its cart, create no order and leave stock at 0. A multi-item checkout that encounters a shortage must roll back every stock deduction.
- Create a fresh multi-store order and cancel one package before payment initialization. Attempt Stripe and PayPal payment on that order: both must refuse, because its original total includes the cancelled package. Create a fresh checkout containing only the remaining items to pay. Historical totals are not evidence of a payable amount.
- On a different unpaid order, initialize a sandbox payment first, then attempt seller cancellation approval. Approval must refuse without changing package status or stock. Race approval against payment startup: either cancellation wins and payment refuses, or startup wins and approval refuses; both must never succeed.
- Complete an actual sandbox payment, verify provider success and signed webhook reconciliation to `Paid`, then exercise delivery, return, partial/full refund and financial reconciliation. A visible iframe or input validation does not pass payment. Cancellation does not pass delivery or refunds. Check actual uploads and Jodit saved content; an existing Cloudinary preview does not pass upload.

Use the normal deployed UI/server actions for these journeys. If direct database writes are needed only for fixture setup, disclose them separately; they cannot prove checkout, stock changes, cancellation, or webhook behavior. Return PASS only for completed actions with before/after evidence. Queue HTTP 503 verifies deliberate deactivation only. SSR metadata verifies crawler-readable tags only; separately test actual social previews.

## Reporting and remaining release checks

For every journey, report actor, exact URL, created record IDs, action, expected/actual result, persistence after reload, console/network/provider errors, cleanup and PASS/FAIL/BLOCKED/NOT RUN. A workflow is PASS only when its required actions and outcomes were executed. Use PARTIAL for rendered pages whose mutations remain untested. Continue independent cases after a blocker. State the precise failed sign-in, fixture creation or provider operation; do not cite read-only authorization as a blocker.

Also verify home/browse/store/product/search/filter/sort/pagination/mobile/share behavior, initial deployed SEO HTML, image responses, robots/sitemap and platform previews. Record real LCP/CLS/INP instrumentation and repeated cold/warm timings plus Vercel Speed Insights; DOM Interactive/DOM Complete are not Core Web Vitals. Source inspection and unit tests must be labeled separately from browser execution. Existing queue endpoints intentionally return 503; test the active signed-webhook/outbox workflows separately.

Coupon reservations currently remain held after failures/cancellations/refunds/chargebacks; automatic release is not implemented. Preserve this fact in the report. Do not delete reservation/audit rows manually to manufacture a passing quota test.

After confirmed failures, provide reproducible steps for a code fix, deploy the reviewed fix, then rerun the failed case and its nearest legitimate control against the new deployment identity. Never label the whole project passed while required CRUD/order/role workflows remain unexecuted.
